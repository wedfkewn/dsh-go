# 静音音频后台方案评估

源码参考：Fish Pocket `a2519ebb24701cc43003ad9ae3a053520216c8a7` 的 BackgroundKeeper/SilentAudio。仅源码与官方模型评估，**未在真机验证**，未加入正式构建。

结论：不采用循环静音维持 Linux 服务。优先官方用户任务续跑；不支持时提示前台运行或远程服务器。

[Apple 审核指南 2.5.4](https://developer.apple.com/app-store/review/guidelines/) 要求后台服务用于其声明用途。仅播放零值 PCM 来维持通用计算不提供用户可感知的音频用途；据此评估存在显著审核风险，不能宣称符合后台音频用途。这是风险判断，不是实际审核结果。

| 问题 | 源码可得结论与待验证内容 |
| --- | --- |
| 音频冲突 | mixWithOthers 减少独占，但不免除音频会话/路由变化；来电及其他不可混音会话可能中断。结束后重启引擎不保证重获授权 |
| 耗电与发热 | 持续音频图加上 Node/Linux 工作增加资源活动；实际耗电、温升、CPU/内存需设备对照，不能给出未经测量数字 |
| 锁屏与低电量 | 配置 audio 模式可能影响调度，但不保证长期连续执行；电源策略、锁屏、系统回收需逐项测量 |
| 内存压力 | 音频不能防止 App 被系统终止；终止后 guest 内存状态不能靠音频恢复 |
| ShellBox 调度 | 若进程获准运行，guest 线程可能获得 CPU；音频不修复阻塞文件读、不改变取消边界、不证明任务正确推进 |
| DSH 连续性 | 网络、模型服务、工具、审批及 guest 阻塞仍会影响完成；必须以实际 taskId 完成事件及持久化结果验证，不能只看播放器或 App PID |

参考实现对 interruption ended/configuration change 重启音频；不应把这种重启移植为反复争取后台资格的策略。若以后有真实语音播放功能，应按实际播放生命周期管理音频，而非让其承担通用保活。
